# Architecture

`wamux-http` is an HTTP edge for the [wamux](https://github.com/LLawli/wamux)
core that speaks the [WAHA](https://waha.devlike.pro/) HTTP API. A client
written against WAHA (n8n's WAHA nodes, a script calling `/api/sendText`, a
webhook receiver) points at this server instead and keeps working.

The core is a pure relay: gRPC over a Unix socket, no auth, no history, no
policy. Everything WAHA does on top of WhatsApp (sessions with names and
config, a message store, webhooks with retries and HMAC, API keys, media files
served over HTTP) is this project's job.

## Contracts

| Contract | Pinned copy | Source |
|---|---|---|
| wamux gRPC | `proto/` (version in `proto/WAMUX_VERSION`) | `crates/wamux-proto/proto` of the core |
| WAHA HTTP | `contract/waha-openapi.json` | `https://waha.devlike.pro/swagger/openapi.json` |

Both are copies on purpose. `scripts/sync-contracts.sh` refreshes them; a
refresh is a change of its own, with the CHANGELOG entry and the code it
forces.

The OpenAPI file is also a test oracle: the contract tests validate every
response body the server produces against the operation's response schema.

## Stack

Go, with these choices measured rather than assumed:

- **Router: chi.** WAHA's paths overlap (`/api/sessions/{session}` and
  `/api/{session}/presence` both match `/api/sessions/presence`). The standard
  library's `ServeMux` refuses 14 of WAHA's 178 routes as ambiguous; chi
  registers all of them and resolves the overlap as WAHA does, static segment
  first.
- **SQLite driver: `modernc.org/sqlite`** (pure Go, no cgo). Measured on 10k
  rows, WAL, 3 rounds: about 10k single-row upserts/s, 67k/s batched, 11k page
  reads/s. `mattn/go-sqlite3` was 15 to 30% faster but needs cgo; the load an
  edge sees is two orders of magnitude below either, and no cgo keeps the
  binary static.
- **gRPC code** is generated by `buf` into `internal/core/wamuxv1` and
  committed. Every tool (buf, protoc-gen-go, protoc-gen-go-grpc, golangci-lint,
  govulncheck) is pinned in `tools/go.mod` and run with
  `go tool -modfile=tools/go.mod`, so the tools' dependency graph never touches
  the binary's.

## Layout

```
cmd/wamux-http/      main: config, store, core client, then app.Wire and serve
cmd/coverage/        writes docs/coverage.md from the routes the server registers
contract/            the pinned WAHA OpenAPI, embedded (operations, test oracle)
proto/               the pinned wamux contract (version in WAMUX_VERSION)
internal/
├── app/             wires every part; main and the tests build the same graph
├── config/          env config (WAHA's variable names where one exists)
├── core/            the only package that speaks gRPC
│   ├── wamuxv1/         generated code (buf generate)
│   └── client.go        connection over the Unix socket, status -> error
├── waha/            WAHA's data model, independent of HTTP and gRPC transport
│                    (ids, WAMessage, payloads, envelopes, mimetypes)
├── store/           persistence behind the `Store` interface, one
│   │                sub-interface per area (ingest, outbound, directory)
│   ├── sqlite/          first implementation, with its own migrations
│   └── storetest/       the conformance suite every engine must pass
├── sessions/        session manager: desired state, leases, pairing, status
├── ingest/          core events -> stored records + WAHA events
├── events/          envelope + webhook selection (publisher), log tail (/ws)
├── webhooks/        outbox workers: delivery, retries, HMAC, custom headers
├── media/           remote fetch (SSRF guard), ffmpeg conversion, /api/files
├── httpapi/         chi router, one file per WAHA tag; auth; error shape
├── fakecore/        in-process wamux server on a Unix socket, for tests
└── testenv/         the whole edge on the fake core, plus the contract checks
```

Dependency direction: `httpapi -> {sessions, store, core, waha, media}`;
`waha` depends on the generated types only. `core` knows nothing of WAHA.

## Sessions

A WAHA session is a wamux account. The session name is the account's
`external_ref`; the core's UUID is stored beside it. The store holds what the
core does not: the session's config (`metadata`, `webhooks`, `ignore`, ...),
its **desired state** (started or stopped), the last QR code, the last status
and the `me` snapshot.

Status mapping (WAHA status <- core state + edge state):

| WAHA | When |
|---|---|
| `STOPPED` | desired state stopped |
| `STARTING` | started, core `CONNECTING`, or connect in flight |
| `SCAN_QR_CODE` | started, not paired, a pairing flow is open |
| `WORKING` | core `CONNECTED` |
| `FAILED` | core `LOGGED_OUT` / `BANNED`, or a terminal disconnect the edge gave up on |

Reconnect after a terminal exit is edge policy (the core never reconnects):
the session supervisor reconnects with backoff while the desired state is
started, except after `LOGGED_OUT`/`BANNED`.

## Several instances

Built so that N edge processes can share one store and one core from the
start, even though SQLite only allows that on one host:

- **Session ownership by lease.** Each session is owned by one instance at a
  time through a row in `leases` (`name`, `holder`, `expires_at`), renewed by
  heartbeat. The owner runs the session's supervisor, its pairing flow and its
  event pump. Losing the lease stops them. `SessionInfo.assignedWorker` is the
  holder.
- **Shared state lives in the store, never in memory**: the QR code, the
  status, the outbox. Any instance answers any request.
- **Event log.** The owner appends each WAHA event to `events` (monotonic id).
  Every instance tails that table for its WebSocket clients, so a `/ws`
  subscriber sees every session no matter which instance owns it.
- **Webhook outbox.** Deliveries are rows claimed with a lock-until timestamp,
  so any instance can deliver and a crash only delays a delivery.
- Idempotency: messages are upserted on `(session, message id)`; the core's
  send echo and a replayed event land on the same row.

## Store

`Store` is an interface whose methods speak domain records, never SQL. The
SQLite implementation uses `database/sql` with its own embedded migration set.
A second engine (Postgres) is another implementation of the same interface
plus its own migrations, and has to pass the same conformance suite
(`store/storetest`).

Timestamps are `i64` milliseconds everywhere in the store.

## Auth

WAHA Plus model:

- `WAHA_API_KEY` (or `WHATSAPP_API_KEY`) is the admin key. `sha512:<hex>` is
  accepted, as WAHA does, so the plain key need not be in the environment.
- `/api/keys` manages more keys: admin or scoped to one or more sessions,
  with the `actions` flags (`read`, `send`, `control`, `setting`, `app`, `delete`).
  Every route declares the action it needs.
- Keys are stored as SHA-256 hashes. The plain key is returned once, when it
  is created; listings return it masked. This is a deliberate difference from
  WAHA, which can return stored keys in full.
- The key is read from `X-Api-Key`, or from the `x-api-key` query parameter
  (WAHA accepts both; the query form is what `mediaUrl` links carry).

## Ids

- Chat ids follow WAHA: `<number>@c.us` for a person (the core's
  `@s.whatsapp.net`), `@g.us`, `@lid`, `@newsletter`, `status@broadcast`
  unchanged.
- Message ids are WAHA's serialized form:
  `<fromMe>_<chatId>_<id>` and, in a group, `..._<participant>`.
- Event ids are `evt_` + lowercase ULID.

## Webhook payloads

Every event has WAHA's envelope: `id`, `timestamp` (ms), `session`,
`metadata`, `engine`, `event`, `payload`, `me`, `environment`. `engine` is
`GOWS`: the schema allows only WAHA's engine names, and GOWS (whatsmeow) is the
closest in shape to `whatsapp-rust`. `_data` carries the core's own message,
which no client should depend on, in any engine.

## What the core cannot do

An endpoint the core has no mechanism for answers `501 Not Implemented` with a
body naming the missing capability, never a fake success. The list is in
[coverage.md](coverage.md) and shrinks as the core grows.

## Testing

- **The fake core imitates the real one, quirks included.** It registers an
  event subscriber only after answering `SubscribeEvents` (as the core's
  forwarder task does) and keeps a replay ring, so an edge that does not
  replay loses the first QR in tests too. It answers `server_timestamp` 0,
  as the core does. A behavior found in the real core belongs in the fake.
- **Every response and webhook is checked against WAHA's OpenAPI.**
  `testenv` validates each body a test receives, and `CheckWebhook` each
  event payload. Where WAHA's document is wrong and its server right, the
  fix is a field-level entry in `specFixes` (`internal/testenv/contract.go`)
  with the reason; a whole-response divergence is the last resort.
- **Store engines share one conformance suite** (`store/storetest`), which
  runs two handles on one database to cover the multi-instance paths.
- **`scripts/live-smoke.sh`** runs the server against a real wamux daemon,
  up to a QR code, with a throwaway store.
